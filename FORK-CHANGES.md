# Отличия от исходного приложения

Что изменено относительно апстрима (NodePass «Anywhere»). Служит и историей работ,
и картой для того, чтобы отделить свои доработки от оригинала.

Состояние на 27 августа 2026.

---

## 1. Переименование в MTurn

`Turn.xcodeproj/project.pbxproj` — `INFOPLIST_KEY_CFBundleDisplayName` в 10 конфигурациях
(iOS, watchOS, tvOS, Network Extension, Widget).

Bundle ID, app group, keychain, URL-схемы, UTI, имена таргетов и папок **не трогали** —
`com.maxorax.turn` везде как было. Причина переименования: имя «Turn» занято в App Store
другим аккаунтом, запись `com.maxorax.turn` создана вручную под именем MTurn.

Не тронуты, хотя содержат слово Turn: User-Agent `Turn/версия` (панель подписки матчит
по нему правила) и глобальный JS-объект `Turn` в движке MITM-скриптов (переименование
сломало бы пользовательские скрипты).

## 2. Версия в одном месте

Новый `Config/Version.xcconfig`:

```
APP_VERSION = 1.0.0
APP_BUILD_NUMBER = 1
```

Подключён как `baseConfigurationReference` к Debug и Release уровня проекта. Все 12
конфигураций таргетов ссылаются на `$(APP_VERSION)` / `$(APP_BUILD_NUMBER)`; литеральных
версий в `project.pbxproj` не осталось.

Тонкость: `$(...)` в pbxproj обязан быть в кавычках, иначе файл перестаёт быть валидным plist.

## 5. Починка холодного старта TURN

Проблема: на старте `shouldRelay` всегда видел «неопознанную сеть» и гонял 10-секундную
пробу даже на Wi-Fi, а первый апдейт path-монитора рвал все соединения.

- `PathMonitorConcurrencyBridge.firstPath(timeout:)` — одноразовое чтение пути.
- `TunnelStack+Lifecycle.seedNetworkContext(isWiFi:isCellular:ssid:)` — засев до старта стека.
- `PacketTunnelProvider.startTunnel` — засев до первого `prepared`; общий хелпер `networkContext(for:)`.
- `TunnelStack+Lifecycle.switchConfiguration` — guard: не рестартовать стек, если конфиг не изменился.

## 6. Починка зацикливания капчи

Проблема: VK отвергал капчу, ядро гоняло фазы `captcha → error → captcha`, шит мигал;
«Закрыть» возвращал его через 3 секунды, выйти было некуда.

- `TurnCaptchaModel.apply(_:)` — переходные фазы `connecting`/`error` не трогают шит.
- `TurnCaptchaModel.suppressed` — «Закрыть» действительно закрывает.
- `TurnCaptchaModel.present()` — вернуться к капче через тост.
- `TurnCaptchaView` — «Закрыть» только убирает шит. Отключать по нему туннель нельзя:
  после решённой капчи шит держится ещё мгновение, и пользователь успевает закрыть его
  сам — соединение обрывалось бы ровно там, где капча только что была пройдена. Отмена
  попытки — работа кнопки питания, которая теперь не блокируется во время подключения.

## 9. Починка залипшего состояния TurnCore

Проблема: тост про капчу вылезал при прямом подключении по Wi-Fi.

- `TurnCore.state` — возвращает `.idle`, если релей не в работе (Go-ядро — долгоживущий
  синглтон и помнит последнюю фазу после остановки).
- `TurnCore.deactivate()` — срабатывает и когда `turn.isRunning()`, даже если учёт потерян.
- `TurnCore.starting` — признак «ядро поднимается прямо сейчас». `active` выставляется
  только после того, как слушатель принял соединение, а `startAndWait` до этого блокируется
  до двух минут, и фаза капчи попадает ровно в это окно. Без этого признака первая версия
  правки выше сообщала `.idle` весь старт: капча не логировалась, уведомление не уходило,
  приложение не показывало шит — и подключение через VK вставало насмерть.

## 9a. Число потоков на один набор кредов

`relay.streamsPerCred = relay.streams` в `PacketTunnelProvider` — все полосы садятся на
один набор кредов, сколько бы их ни было. Каждый набор — это отдельный вход гостем в
звонок, а вход VK встречает капчей; причём не только на старте, потому что креды живут
девять минут (`credentialLifetime - cacheSafetyMargin`) и каждый кэш ходит за новыми сам
по себе. На дефолтной десятке это ровно раскладка Cascade LTE, у которого поля
`streamsPerCred` в профилях нет вообще.

Проверено на устройстве 2026-08-29: один `[VK Auth] Success`, дальше девятнадцать полос с
`Using cached credentials (cache=0, …)`, все двадцать поднялись за 22 мс, ни одной
`setup error`, второй капчи не было.

⚠️ Значение из подписки (`defaults?.streams_per_cred`) не используется. Если понадобится
вернуть панели управление — убрать эту строку.

## 9b1. Bond выключен, и приборы, которыми это доказано

`relay.bond = false`. Bond размазывает **одно** TCP-соединение по всем полосам, и в
журнале видно, чем это кончается: speedtest открыл 35 соединений за три секунды, каждое
разошлось по двадцати полосам — семьсот smux-потоков разом, footprint 18 → 25 → 35 МБ и
процесс сняли. Строки `[VPN] Tunnel stopped` при этом нет вовсе: расширение убивает
jetsam, `stopTunnel` не выполняется. Трафик, который сам открывает соединения пачками, в
бонде не нуждается — без него каждое соединение живёт на одной полосе.

`TurnCore.coreMemoryBudget` держит окно KCP на 128 пакетов через `setenv` до старта ядра.
256 пробовали и сняли: суммарная скорость почти не изменилась (13.6 против 11.8 Mbit/s),
но ядро гоняет KCP с выключенным управлением перегрузкой, поэтому окно работает как
размер залпа в одну аллокацию VK — отдельные соединения начали залипать. Поднимать его
можно только вместе с `VK_TURN_KCP_NC=0`.

`TurnStreamCount.maximum = 20` — ограничение по памяти, не по VK: сорок полос в
расширение не влезут никогда.

Три прибора, без которых всё это не измерялось бы:

- `TunnelLogFile` — дублирует журнал в `Library/turn.log` внутри App Group. Журнал в
  памяти умирает вместе с процессом, а именно убитый процесс и интересен. Файл снимается
  с устройства без root: `xcrun devicectl device copy from --domain-type
  appGroupDataContainer --domain-identifier group.com.maxorax.turn --source
  Library/turn.log`.
- `startMemoryWatch()` — раз в 5 секунд пишет `[VPN] Footprint N MB, relay lanes N/M`.
  Последняя строка перед обрывом и есть диагноз.
- Счётчик живых полос в Настройках (`TurnState.activeStreams`), вычитанный из строк
  ядра `(active: N)` — единственного места, где оно публикует размер пула сессий.

В Debug-сборках ядро запускается с `debug: true` (`TurnCore.coreDebugLogging`), в Release
молчит: строки несут адреса реле, а журнал предназначен для передачи.

## 9b. Привязка сокетов релея к физическому интерфейсу

`PacketTunnelProvider.bindRelay(to:)` зовёт `TurnCore.bind(toInterface:)` — то, что
предписывает заголовок gomobile («call this when NWPathMonitor reports a network change
so subsequent reconnects bypass the active utun») и чего в проекте не делалось ни разу.
Интерфейс выбирается как первый в `path.availableInterfaces` с типом не `.other` и не
`.loopback`: `.other` — это и есть utun туннеля.

⚠️ **Сейчас не вызывается.** Привязка включилась в 8cb2ecf в 18:05 27 августа, за
19 минут до этого в 2250c1f менялась раскладка потоков по кредам, и speedtest через релей
сломался где-то в этой паре. Привязка снята, чтобы посмотреть на релей без неё; сам метод
оставлен на месте. Перед возвратом надо починить две вещи: интерфейс выбирается по порядку
в списке, а не по типу, который сообщает сам путь (`path.usesInterfaceType`), и
`setBindInterface` действует только на сокеты, созданные после вызова, поэтому
перепривязка посреди сеанса разводит полосы по двум интерфейсам. Вернуть её обязательно
до включения `includeAllNetworks`: эта настройка загоняет сокеты релея в тот самый
туннель, который они питают.

**Порядок в `startTunnel` менять нельзя.** Apple рекомендует не звать
`setTunnelNetworkSettings`, пока провайдер не готов передавать пакеты, а `prepared()`
может ждать до двух минут. Перестановка была сделана и **сломала VK TURN**: сокеты релея
устанавливаются до появления туннеля, и применённый следом маршрут по умолчанию их
рушит — капча проходила, а соединение не вставало. Откачено.

Из-за этого сохраняется окно, в котором туннель поднят, но ничего не пропускает.
Закрывать его надо ограничением времени на `prepared()` с асинхронной дозагрузкой релея
(рекомендация №7 из обзора), а не перестановкой.

## 10. Про-режим и простой главный экран

Тумблер «Про режим» (`AppSettings.proMode`, хранится в App Group через
`AWCore.getProMode()`), по умолчанию **выключен**. Он делит приложение на два вида.

**Обычный режим** — две вкладки, Главная и Настройки.

Главный экран: кнопка питания со статусом и таймером, под ней список серверов
обычным `List` — со свайпами Edit/Delete, контекстным меню, замером задержки по
тапу и сворачиваемыми группами подписок. Сверху в тулбаре «+» (добавить
конфигурацию) и меню «…» с двумя действиями: замерить задержки видимых серверов
и обновить все подписки. У каждой подписки в заголовке свои иконки обновления и
замера.

Статистики здесь нет, а значит нет и второй страницы — поэтому `DetailRevealScrollView`
с его снапом не задействован, и `List` не конфликтует со скроллом.

Настройки в обычном режиме: Про режим, обновление подписок, Routing Rules, Logs,
Requests, About.

**Про режим** — возвращается вкладка Proxies и прежний главный экран с капсулой
выбора и статистикой по свайпу вверх. В настройках добавляются iCloud Sync,
Personalization, Always On, Global Mode, AD Blocking, Country Bypass, секции
Security (включая VK TURN) и Utilities, а также Advanced Settings.

Обработаны два перехода: выключение про-режима на вкладке Proxies сбрасывает выбор
на Главную, а диплинк с прокси-ссылкой ведёт на Главную, если вкладки нет. Секция
Routing не рисуется, если Global Mode включён вне про-режима — иначе она была бы
пустой и выключить его было бы нечем.

⚠️ AD Blocking и Country Bypass видны в про-режиме, но не работают: правил в
`Rules.db` нет. У тех, кто успел включить блокировку рекламы, в App Group осталось
назначение `ADBlock → REJECT` — при появлении настоящей базы оно сработает само.

## Как устроена история

```
mturn   Split the app into a pro mode and a plain one
        Fork changes on top of upstream Anywhere
        Vendor the TurnCore and TurnRules local packages
        Rename Anywhere identifiers to Turn
        Rename the Anywhere tree to Turn
main    ← нетронутая точка апстрима (70075d9)
```

`main` намеренно оставлен там, где был: это эталон оригинала. Сравнить с ним —
`git diff main mturn`.

**Почему переименование разбито на два коммита.** Сначала идут только перемещения
файлов, с сохранением тех же блобов — git записывает их как переименования со 100%
сходства, и все 272 распознаются как таковые. Замена идентификаторов внутри файлов
идёт следующим коммитом. Благодаря этому мердж апстрима сможет сам сопоставлять
`Anywhere/Views/...` с `Turn/Views/...`, а не гадать по эвристике на дереве в 557 файлов.

**Вендоренный Go-core вынесен в отдельный коммит** (`Vendor the TurnCore...`) —
108 МБ бинарников в `Mobile.xcframework`. Изолированы намеренно: перевод в Git LFS
означает переписать один коммит, а не выковыривать бинарники из коммита с исходниками.
`.git` из-за них вырос с 15 до 54 МБ, и каждое обновление ядра добавит столько же
навсегда. Решать это дешевле сейчас, чем через десяток обновлений.

## Как вливать апстрим

Замер расхождения на момент форка: из 557 исходников апстрима **87% отличаются только
переименованием** (484 файла, содержимое идентично после подстановки `Anywhere` → `Turn`),
и лишь 11% (61 файл) изменены по-настоящему. То есть подавляющее большинство будущих
конфликтов будет возникать из-за косметики, которой пользователь не видит: имя в App
Store задаётся одной строкой `INFOPLIST_KEY_CFBundleDisplayName`, а не именами папок,
таргетов и типов.

Перед первым мерджем стоит настроить:

```
git remote add upstream <адрес апстрима>
git config rerere.enabled true
```

`rerere` запоминает разрешённые конфликты и применяет те же решения при следующем
мердже — для форка, который раз за разом натыкается на одни и те же коллизии
`Anywhere`/`Turn`, это экономит больше всего времени.

**Дисциплина, снижающая цену мерджей:** новая функциональность — отдельными файлами,
а не правками внутри апстримных. Здесь так и сделано с `AboutView`, `LogArchive`,
`ConnectionStageToast` — апстрим о них не знает, конфликтовать не с чем. А `HomeView`,
`MainTabView`, `SettingsView`, `PacketTunnelProvider` правились внутри, и каждая такая
правка — будущий конфликт. Где возможно, сводить вмешательство в чужой файл к одной
строке, вызывающей свой код.

## Известное, но не сделанное

Из обзора устойчивости переключения «прямое ↔ VK TURN» остаётся 11 пунктов из 12
(исправлен только первый). Самые тяжёлые:

- решение о релее принимается однократно, по одной пробе, без ретраев и гистерезиса;
- смерть прямого пути **без** смены класса интерфейса не замечается вообще;
- из релея нет пути назад, пока сеть та же;
- `startTunnel` может ждать до ~130 с при системном вотчдоге около 60 с;
- гонки вокруг `prepared`/`TurnCore` (провайдер не актор);
- в режиме `.always` неудачный запуск релея тихо уходит в прямое и больше не пытается.

Отдельно: бандлящаяся `LocalPackages/TurnRules/.../Rules.db` — пустая заглушка
(0 правил). Из-за неё не работают блокировка рекламы, обход по стране и встроенные
сервисные наборы правил. Историческая база на 1.5 МБ есть в git:
`git show cefe495^:Shared/DataStore/Rules.db`.

Тестовый таргет не собирается из-за устаревшего `Turn Tests/TurnLinkTests.swift`
(`TurnSubscription.Parsed` поменял форму) — не наша правка, но блокирует прогон тестов.
